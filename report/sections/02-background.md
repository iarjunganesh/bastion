## 2. Background and related work

**End-to-end confirmation and partial failure.** Saltzer, Reed and Clark argue that a function such as reliable delivery can be implemented completely and correctly only with knowledge held at the endpoints. Lower-layer mechanisms can improve performance, but they cannot replace an end-to-end check. [R6] Bastion's completion controls apply this argument inside an agent workflow. The fact that a transport returned, a stream closed or a remote task reported no error does not show that a review record exists. Only the step that created the record can confirm it, and the investigation is complete only when that confirmation reaches the dispatcher. Huang et al. describe gray failure: a component is unhealthy from the perspective of some observers but not others, which they call differential observability. [R7] Several of Bastion's failures are of this kind. The worker knew its task had failed, but the caller saw a successful, empty event. Yuan et al. found that many catastrophic failures in data-intensive distributed systems came from incorrect handling of errors that the software had already signalled, and that simple tests of error-handling code would have exposed many of them. [R8] Bastion's history adds an agent-specific variant, in which the error signal never became an error at the next hop.

**Structural defences for large language model (LLM) agents.** Debenedetti et al. introduce CaMeL. It separates control flow from data processing and uses an interpreter that tracks provenance and capabilities, so that security checks do not depend on the model's discretion. [R1] Beurer-Kellner et al. describe design patterns that keep untrusted data away from an agent's control flow, including plan-then-execute and context minimisation. [R2] Bastion follows the same principle in a narrower, application-specific form. The workflow is fixed, the IAM rules are deterministic, and the model writes only a bounded explanatory field. There is no model-generated program and no general capability tracker. This is a design comparison, not an empirical one.

**Explanation and decision provenance.** Turpin et al. show that chain-of-thought explanations can omit the features that actually drove a model's prediction. [R3] Bastion's decisions are made by deterministic rules, not by the model. Their result nevertheless motivates keeping the explanation separate from the record of where a decision came from. Bastion's canonical comparison checks that structured findings survive the model unchanged. It does not show that the rationale is faithful or useful to a reviewer; that question belongs to the deferred C4.

**Data minimisation and access review.** Article 5(1)(c) of the General Data Protection Regulation (GDPR) states the data-minimisation principle. [R4] Here it motivates an engineering boundary; no compliance determination is made. Pseudonymous identifiers and regional placement do not establish anonymity or end-to-end EU model residency. Google's IAM role recommendations use permission-usage data to flag excessive roles. [R5] Bastion's detector is deliberately much narrower: it flags only Owner and Editor grants.

**Agent frameworks and remote agents.** The Agent2Agent (A2A) protocol defines how independently deployed agents exchange messages and tasks. [R10] Bastion composes its workflow in Google's Agent Development Kit (ADK), with two remote workers reached over A2A. In ADK, each agent run owns its session state, and a remote agent does not share the caller's session. Upstream maintainers confirmed these per-agent semantics as intended behaviour after Bastion reported the consequences. [U1–U4] Section 6 records where Bastion's design wrongly assumed otherwise. To the author's knowledge, no published study measures whether agent frameworks preserve local execution contracts once sub-agents become remote. Section 9 proposes one. This report does not claim that the failure class is new, only that it is documented here, with dates, in one deployed system.
